## 1. Why R4 exists

The R3 rescore (`docs/audit/13_ACCURACY_100_REPORT.md`) reached F1 1.000,
precision 1.000, recall 1.000, FP rate 0.000 — on the SAME 210-project
corpus whose failures motivated the fixes, with the same labels and the same
scorer. That is a regression check, not independent evidence: the fixes were
tuned against exactly the failures they then "passed". R4 is the fresh
blind test that decides whether the accuracy-100 fixes generalize to unseen
code, or only memorized R3's corpus. R4's verdict — not the rescore — is the
evidence that may or may not support any superiority claim.

**Bottom line up front:** the fixes largely generalize. On unseen code
Aegis holds precision 1.000 and FP rate 0.000 with recall 0.853
(F1 0.921) — far above R3's 0.733 and R2's 0.367 — but the 20 false
negatives show the fixes did not generalize completely, and the FP-rate
tie with KICS means the pre-registered win condition is not met.

## 8. Reconciliation: why rounds 2, 3, rescore, and 4 differ

| Round | Corpus | Scorer / GT scope | Aegis F1 | Aegis FP rate |
|---|---|---|---|---|
| 2 | 205 projects, 416 firm concepts | min-counting, full FP adjudication (Aegis/Checkov), 400-samples (KICS/Trivy) | 0.367 [0.323, 0.411] | 0.733 |
| 3 | 210 projects, 150 firm critical/high concepts | same method, narrower GT (critical/high only) | 0.733 [0.674, 0.790] | 0.314 |
| Rescore | SAME 210 projects as R3, same labels/scorer | post-fix regression check | 1.000 | 0.000 |
| 4 | 210 NEW projects, 136 firm concepts | same method as R3 + 8 new classes, classifier normalization fixes | 0.921 [0.880, 0.955] | 0.000 |

Three distinct causes, not one:

1. **Different corpora.** R2's 416-concept universe included many more
   medium/low classes and harder fixtures; R3 narrowed to 150
   critical/high concepts; R4 has 136 concepts on fresh code with new
   blocks and new shape variants (Bicep for-loops, CFN intrinsics). The
   F1 numbers are not comparable across rounds without this caveat — the
   denominator changed each time.
2. **Different scorers / GT scope.** R2→R3 changed the firm-concept
   universe (critical/high only) and the adjudication tables; R3→R4
   added 8 classes and fixed 3 classifier normalization gaps. R4 also
   deliberately added NO semantic title→class mappings (R3 had 10),
   which costs Aegis 8 near-miss FNs in R4 that R3's method would have
   partially rescored.
3. **Tuning.** The rescore's 1.000 was measured on the same corpus the
   fixes were tuned against — it is a regression check, not evidence.
   R4 is the first independent measurement: 0.921, i.e. the fixes
   generalized substantially (0.733→0.921 vs R3's corpus, 0.367→0.921 vs
   R2's) but not perfectly (20 FNs, §5.6). The gap between rescore 1.000
   and R4 0.921 is the tuning premium: ~8 points of F1 that did not
   survive contact with unseen code.

The honest reading: Aegis improved enormously from R2→R4, the accuracy-100
fixes are real and largely general, but the "1.000" was never the true
generalization number — 0.921 on fresh code is.

## 9. Limitations

- **Single-agent labeling.** Both labeling passes were performed by the
  same agent (procedural, not personal, independence) — same limitation as
  R3, disclosed in protocol §3. Class-level agreement was 97.1%, which
  bounds but does not eliminate labeler bias.
- **Matcher near-misses.** 8 of Aegis's 20 FNs are findings that exist but
  don't map to GT classes (no semantic mappings added post-results, by
  design). Aegis's "true" detection recall is higher than 0.853; the
  reported number is the classifier-mediated recall.
- **KICS FP rate is sample-based.** KICS's 0.000 comes from a 400-sample
  with zero FPs; the extrapolated FP count is 0.0 but the true rate has
  sampling uncertainty the bootstrap's binomial redraw captures (the
  fp_kics-aegis difference CI is degenerate [0,0] because both point
  estimates are exactly zero — the CI reflects the observed data, not a
  claim that KICS can never FP).
- **Timing under contention.** All timing runs happened under heavy VM
  load (6 parallel workers). KICS's early timing runs were inflated
  (55–103 s); the median is robust, but absolute timings are
  contention-affected. Ratios are so large (44–176×) that no plausible
  contention correction changes criterion (c).
- **Synthetic corpus.** All 210 projects are generator-built, not real
  repositories. Real-world code has messier shapes (modules, dynamic
  blocks, cross-file references) that this benchmark does not exercise.
- **Checkov Bicep/Dockerfile and KICS Pulumi/Dockerfile zero-match.**
  These scanners nominally support those formats but matched zero firm
  concepts — whether that reflects check coverage or corpus shape is not
  distinguished by this benchmark.
- **R3 adjudication corrections.** Two R3 adjudication decisions were
  corrected in R4 after code verification: CKV_AWS_8 is the EBS-encryption
  check (TP), not "launch configuration description" hygiene; and the
  KICS/Checkov hygiene tables' probe/logging asymmetry is inherited from
  R3 as-is (both verdicts exclude findings from the FP numerator, so the
  comparison is unaffected).
